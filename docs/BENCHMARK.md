# 怎样测出可靠的对比图

先区分两个问题：**并发下载机制是否有效**，以及**这台iPhone实际看视频是否更顺畅**。目前可以复现前者的受控实验，也可以不用新App记录后者；还没有可比较原生App、旧Redirect与自动版全流量的手机Mbps测量器。

## 已完成：本机HTTP实验

![并发分片受控实验](../pics/concurrency-fixture.png)

- Windows / Node.js24.12.0，2026-10-13本机测量；真实HTTP回环请求，不接触B站媒体地址。
- 相同4 MiB字节、初始等待120ms、每任务每tick最多16 KiB，tick目标16ms；实际系统调度不保证精确16ms。
- 1/2/4/8/16/32任务，128 KiB片下限，每条件3轮，轮次间正反交替顺序，共36次完整下载。每次校验全部字节相等。
- 两种预设：仅每任务配额，以及额外限制每tick最多4份16 KiB总出口配额。后者模拟共享瓶颈。
- 有效交付率 = `验证完成的总字节 × 8 ÷ 完整下载及校验墙钟秒数 ÷ 1,000,000`。图为3轮中位数，误差线为最小—最大值，不是置信区间；两个面板同一纵轴。

| 配额模型 | 单任务 | 4任务 | 8任务 | 16任务 | 32任务 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 仅每任务限速 | 4.84 | 17.53 | 33.29 | 54.74 | 89.96 |
| 额外总出口配额 | 5.13 | 18.70 | 19.08 | 18.83 | 17.38 |

单位Mbps。数值为这次实际执行的受控模型，不是iPhone、宽带或海外CDN性能；不用于宣传手机提速倍数。4 MiB/128 KiB的32任务也不能替代手机日志中1 MiB/32 KiB策略的结果。原始数据见[concurrency-fixture.json](../benchmarks/concurrency-fixture.json)，实际服务器并发峰值也在其中。

## 先做手机体验对照：不用安装新App

### 比较什么

第一阶段只比较两种方案，减少工作量：

- A：原Redirect插件，停用Range。
- B：Bili Range自动版，停用原Redirect。

需要三柱图时，再加入C：停用两种加速、Loon保持相同运行方式。所有方案都保留相同Wi-Fi、直连/代理线路、DNS、清晰度、倍速、HDR/编码偏好、录屏方式和观察时长。不要同时测换DNS与加并发。App不能锁定的条件如实际编码、CDN缓存，要明确记为未控制。

这是**完整使用方案比较**：节点选择、下载开销和失败回退都可能影响结果；它不能单独证明并发的因果收益。

### 一组怎样跑

1. 选你当前账号能播放、又容易复现问题的视频段。记住同一个起始位置，固定可选清晰度与倍速。为减少同一个片段的特殊性，先做3个不同视频段。
2. 每个视频段随机选择 **ABBA或BAAB** 顺序，共4轮。每轮只启用对应方案，回到相同视频起点；首帧后观察固定60秒。三段共12轮，A/B各6轮。设置切换完成后再开始计时，给所有方案同样的准备过程。
3. 用iPhone自带录屏，记录“点击播放”到首个视频画面的时间；再记录这60秒内因等待加载而停止推进的次数与总时长。主动暂停、拖动或切到后台不算缓冲卡顿。帧时间与人工判读有误差，保留原视频作私下复核。
4. 从Loon请求记录确认观察片段确实发出了新的媒体请求；无法确认、命中App缓存、实际清晰度变化或中途换网络的轮次标记无效。保留无效记录及原因，重做整个对照块，不只删掉表现差的一轮。新请求本身也不能证明远端CDN是冷缓存。
5. 结束后立即取B方案短诊断，核对实际处理版本、失败/预算放行；诊断作解释资料，不把接管样本Mbps当作A方案的同口径速度。

若加入C，每个视频段按随机顺序各做两次A/B/C，所有方法在同一块中次数相等；例如抽取一个排列，再反向走一遍。先预定顺序与样本数，不看结果再决定停止。分块与随机化的思路参考[NIST随机区组设计](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)；这里是受缓存与网络时变影响的观察性真机对照，并非严格实验室随机试验。

### 记录与出图

复制空白[phone-results.template.csv](../benchmarks/phone-results.template.csv)到本地私有目录 `benchmarks/phone-private/` 后填数。这里没有示例“测速值”，也没有预填0卡顿。

| 字段 | 填什么 |
| --- | --- |
| session / block / video_label | 这次会话、对照块编号、视频段别名；不要填完整媒体URL |
| method / order | redirect、auto；可选native，及块内第几轮 |
| quality / playback_rate | 相同的画质选择及倍速 |
| duration_s | 首帧后固定观察60秒 |
| startup_s | 点击到首帧的秒数 |
| stall_count / stall_seconds | 观察窗口内缓冲停顿次数、总秒数 |
| new_transfer_confirmed | 确认新的媒体请求填yes；无法确认的轮次不进入可比数据 |
| notes | 私下记录准备、缓存、温度或异常；不自动发布 |

绘图器要求同块所有方案、等次数、相同画质/倍速/时长、唯一轮次编号及至少每方案3条有效观察。空模板、未确认传输和不平衡块会拒绝绘图。图展示**首帧秒数、每分钟卡顿秒数**的中位数与最小—最大值，清楚注明体验指标，不冒充Mbps。

```sh
python scripts/render-benchmark.py --phone benchmarks/phone-private/results.csv --out-dir benchmarks/phone-private/figures
```

私有目录被Git忽略，工具不上传数据。发布手机对比图前先检查录屏/记录中的私人信息、公开测量条件和无效轮次；图片应有日期、地区/线路概况、方案版本、视频条件与样本数。

## 如果一定要测“下载Mbps”

需要同口径的工程测量：合法且未过期的**同一媒体地址、完全相同字节范围、同一节点和协议偏好**，在手机同一测量环境中分别用单任务及并发任务下载；核对206、Content-Range、总长度、实体和字节数，并统计包括失败耗时的完整尝试。将DNS/连接准备、缓存状态与错误率一起报告。单任务与8任务的图只能称为“固定媒体Range下载对照”，不等于原生App、原Redirect与自动版整体性能。

当前默认诊断只见已完成接管流量，不能可靠测出原生/旧插件的全部媒体字节。Loon若只在响应头时回调，也不能用Content-Length除以头部等待时间当作吞吐；为了记录而强制缓冲原生响应又会改变基线。因此**目前不画三种方案的手机Mbps图**。后续需要实现并真机验证同字节测量入口，或在所有方案中加入同一个可核对字节/完整时间的测量层，再单独验证该测量层的开销。

已有的11.49/5.46 Mbps观察来自不同时间、缓存与分片条件，不能直接命名为“原生vs加速”柱图。它们保留在[证据说明](EVIDENCE.md)，不替代新的配对测试。

## 复现实验图与流程图

```sh
node scripts/benchmark-concurrency.mjs
python scripts/render-benchmark.py --fixture benchmarks/concurrency-fixture.json --out-dir pics
python scripts/render-benchmark.py --flow --out-dir pics
```

绘图需要可选Python+Matplotlib和中文字体；Windows使用微软雅黑，Linux可使用思源/Noto CJK。它不属于Loon运行或默认Node构建/CI依赖。生成SVG与PNG，原始JSON不由绘图器伪造。

`--small`模式另测1 MiB、32 KiB下限并写到small-chunk-fixture.json；不要把不同模式混画成同一条件。每次复测会因本机调度改变数值，更新图时同步原始数据、日期和说明。
