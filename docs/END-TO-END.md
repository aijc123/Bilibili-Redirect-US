# 全链路优化：目标与证据

目标持续进行中。用户已明确反馈0.1.17在官方App、1080高帧率、1倍速仍会停顿；这条反馈优先于自动检查或早先“基本顺畅”的记录。以同Wi-Fi直连为当前场景，手机不新增App，日常一个启用开关，长期订阅保留。更高码率与4K/1.5倍速不能由1080测试代替。

## 最新发现

用户在0.1.18上完成相同897,932字节的手机媒体测试。原地址Akamai配置1任务为20.92Mbps、配置8实际6任务为27.21Mbps，均2/2成功；替换后的4个节点成功中位约2–3.5Mbps，还出现跳转拒绝、网络错误和实体冲突。[整理后的用户摘要](../benchmarks/phone-media-2026-10-14.json)保留统计口径，不包含签名地址。

这不是原生App对照，也没有确认媒体轨类型，每档最多2次，仍有缓存与时间噪音。它支持修正“默认排除原地址”的策略，不能声称得到了长期节点排名、因果提速倍数或无卡顿结果。

第二轮1 MiB原地址1/8任务20.35/33.43Mbps，均成功；但0.1.19实际接管随后出现59秒新增17次网络错误，近期窗口19次完成尝试中9次失败。两类数据不矛盾：手动测试暂停播放、逐组进行，实际播放有请求重叠且官方源会变化。[不含地址的第二轮数据](../benchmarks/phone-media-2026-10-14-run2.json)与[接管观察](../benchmarks/phone-playback-0.1.19-2026-10-14.json)分别保留。[独立0.1.20候选](PREVIEW.md)验证错误退让、单任务恢复及小范围调优，0.1.19订阅保持原状。

用户随后说明本轮0.1.19“好像是杜比视界1倍速，超级卡”：清晰度待确认、严重卡顿明确，当前目标没有完成。旧SIDX表示不能确认当前杜比视界的码率；暂停播放的短测不代表连续供给。0.1.20首先需要复测这次卡顿视频，并另行验证此前1080高帧率条件。

## 如何验收

先在本轮卡顿的同一视频、用户确认的清晰度、1倍速和相同Wi-Fi上确认实际请求版本为0.1.20，并查看“媒体选路”和“接管保护”。记录首次播放、连续播放至少10分钟（视频较短则完整播放）和拖动后的实际停顿；出现停顿时立即保留短诊断。另行复测此前1080高帧率条件，再扩大到至少3条视频。保持其他条件一致，与原生App路径或原Redirect按[体验对照方法](BENCHMARK.md)比较。

工具不能读App真实缓冲、实际清晰度、解码负载与卡顿计数；这些需要用户或录屏证据。若仍卡，继续以媒体交付、失败等待和系统负载定位；若当前链路不足以供应目标码率，应报告约束及替代路线的实际验证情况，不能把目标改成较低清晰度后宣称完成。

0.1.19另用真实回环HTTP对比旧0.1.18，确认旧策略会转到模型中的慢替换节点、新策略保留原地址，全部字节一致。[原始模型数据](../benchmarks/routing-fixture.json)与[复现脚本](../scripts/evaluate-routing.mjs)公开。延迟是模型指定的，不是对手机结果的复刻，更不能替代以上播放验收。

## 杜比视界是不是必须50–100Mbps

不能只凭格式名称设定统一下载门槛。[Apple官方HLS示例](https://developer.apple.com/streaming/hls-authoring-specification-for-apple-devices.html)包含杜比视界1080p平均约8Mbps、峰值约12.9Mbps的变体。这不是B站码率，也不用于估计当前视频；实际需求还受分辨率、帧率、编码和内容影响。用户提出的50–100Mbps可以作为希望达到的能力目标，但目前没有证据确认本次表示必需该速率。

若实际媒体持续需要50Mbps，而当前路径持续只能交付33Mbps，单靠改变任务数或等待就不能长期维持播放。反过来，单次超过需求也不充分：连接失败、慢分片和重试间隙都可能消耗缓冲。对这条插件路径，目标是有效媒体交付长期跟上消费，并能覆盖波动；当前统计不含放行流量、也读不到播放器缓冲，不能直接代入最近窗口计算完整App的供需差。

Loon接管返回前必须等完整范围，最慢分片会阻塞本次交付。桌面BTR还能控制网页播放器的预取和缓冲；官方App的请求大小、缓冲、解码和倍速不由本插件控制。因此不会把浏览器成绩或本机32任务模型当成手机能力上限/下限，也不把调整DNS当作补足持续媒体吞吐的保证。[DNS连接IP研究](DNS-RESEARCH.md)仍缺设备能力与真实媒体证据。
