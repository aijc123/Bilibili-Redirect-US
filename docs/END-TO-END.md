# 全链路优化：目标与证据

目标持续进行中。用户已明确反馈0.1.17在官方App、1080高帧率、1倍速仍会停顿；这条反馈优先于自动检查或早先“基本顺畅”的记录。以同Wi-Fi直连为当前场景，手机不新增App，日常一个启用开关，长期订阅保留。更高码率与4K/1.5倍速不能由1080测试代替。

## 最新发现

用户在0.1.18上完成相同897,932字节的手机媒体测试。原地址Akamai配置1任务为20.92Mbps、配置8实际6任务为27.21Mbps，均2/2成功；替换后的4个节点成功中位约2–3.5Mbps，还出现跳转拒绝、网络错误和实体冲突。[整理后的用户摘要](../benchmarks/phone-media-2026-10-14.json)保留统计口径，不包含签名地址。

这不是原生App对照，也没有确认媒体轨类型，每档最多2次，仍有缓存与时间噪音。它支持修正“默认排除原地址”的策略，不能声称得到了长期节点排名、因果提速倍数或无卡顿结果。

## 链路逐项状态

| 环节 | 目前证据与处理 | 尚缺什么 |
| --- | --- | --- |
| 官方地址与候选 | 0.1.19保留官方原地址；即使其他节点有历史成功分数，也不直接替换它。原地址异常时才使用候选；没有固定某个Akamai主机 | 新版在相同视频上的连续播放反馈；工作正常但持续较慢的原地址如何低成本比较仍待研究 |
| DNS | 原DNS诊断有真实查询结果；切网预热优先包含最近实际源主机，保持最多4个域名、2路查询，不改全局配置 | 同一手机路径下，各DNS返回IP的HTTPS媒体吞吐比较；公开单请求API未确认IP覆盖方式 |
| 并发与预算 | 128KiB片下限、常规8任务、负载/错误收缩、有限相邻档比较；不把任务数当物理连接数 | 真机同条件并发收益；大量不足1MiB的实际请求仍不参与4/8收益比较 |
| 慢分片与交付 | 记录完整交付与分片耗时差，严格完整范围后返回 | Loon接口没有浏览器的流式进度/取消能力；整段受最慢片影响仍存在 |
| 失败回退 | 同地址签名/协议/节点/网络的失败记忆；明确拒绝保留60秒，重复网络错误休息12秒；另一表示的成功不能抹掉它 | 实际失败等待减少多少；原请求放行后的完整下载与App缓冲不可直接测得 |
| 内容正确性 | 206、范围、长度、总长、实体与重定向校验保持；本机真实HTTP下载核对每字节 | 不能由自动检查推出所有B站内容、系统与协议路径零缺陷 |
| 网络变化 | 清评分、清调优与失败记忆、保留在途租约，旧回调不复活旧数据，预热实际源域名 | 真机切换网络后恢复情况；DNS缓存及系统连接池不可完全控制 |
| 播放体验 | 0.1.17已确认仍卡顿；0.1.18有真实固定媒体Range对照 | 0.1.19同视频1080高帧率1倍速，以及更高码率/倍速的首开、连续播放与拖动验证 |

## 如何验收

先在刚才卡顿的同一视频、1080高帧率、1倍速和相同Wi-Fi上确认短诊断显示“媒体选路：保留官方原地址”。记录首次播放、连续播放至少10分钟（视频较短则完整播放）和拖动后的实际停顿；出现停顿时立即保留短诊断。逐步扩大到至少3条视频，包含较高码率/倍速场景。保持其他条件一致，与原生App路径或原Redirect按[体验对照方法](BENCHMARK.md)比较。

工具不能读App真实缓冲、实际清晰度、解码负载与卡顿计数；这些需要用户或录屏证据。若仍卡，继续以媒体交付、失败等待和系统负载定位；若当前链路不足以供应目标码率，应报告约束及替代路线的实际验证情况，不能把目标改成较低清晰度后宣称完成。

0.1.19另用真实回环HTTP对比旧0.1.18，确认旧策略会转到模型中的慢替换节点、新策略保留原地址，全部字节一致。[原始模型数据](../benchmarks/routing-fixture.json)与[复现脚本](../scripts/evaluate-routing.mjs)公开。延迟是模型指定的，不是对手机结果的复刻，更不能替代以上播放验收。
