# 效果证据与测试范围

本项目的说明基于手机反馈、请求层观察和自动检查。三者用途不同，分别记录；下面不公开原始手机日志、媒体标识或签名地址。

| 证据 | 观察到什么 | 能说明什么 |
| --- | --- | --- |
| 0.1.3真实iPhone对照 | 用户确认同视频、同清晰度、同Wi-Fi直连，对比原Redirect后感觉更流畅、快了不少 | 这台手机有积极体验反馈；没有测出因果倍数 |
| 0.1.12请求层观察 | 同网络轮次、同媒体表示组、同08c节点中，8路/128 KiB成功样本中位11.49 Mbps；32路/32 KiB为5.46 Mbps | 更支持先用8路策略；时间、精确Range大小/位置、缓存及分片下限未匹配，不能说8路造成2倍提速 |
| 0.1.13实际体验 | 用户反馈“基本顺畅”，当轮主要为小请求与低码率已见表示 | 大量小请求放行并不等于卡顿；不能拿这一轮证明高码率4K能力 |
| 0.1.14自动版 | 167项检查、GitHub构建复现和公开文件获取通过 | 支持实现正确性；自动收缩的净收益仍待真机反馈 |

上面的11.49/5.46是每请求成功样本分布，8路组21次尝试、19次成功，32路组83次尝试成功；样本和设置条件不能被当成完整播放器随机对照。最近交付率只统计已完成接管尝试，不含小请求等放行流量，也没有App缓冲或卡顿计数。

## 两个参考资料分别做什么

- [chrisliu298的benchmarks.md](https://github.com/chrisliu298/bilibili-cdn-fix/blob/main/benchmarks.md)：2026-06-11美国单线路历史测速，作为hwo1/08c候选来源；不是本项目手机测速。
- [BTR](https://github.com/MrTangLuyao/Bilibili-thread-ripper)：桌面网页环境的实现、测试与展示；其效果不能替代本项目iPhone证据，也没有把其速度图移成本项目结果。

GitHub Actions的[data/cdn-health.json](../data/cdn-health.json)只做Runner DNS/TLS健康探测；mediaMbps仍为null，不能据此认定某节点视频可用或改变手机的最快节点。[探测说明](CDN-HEALTH.md)

## 下一轮怎样提供有用反馈

保持同视频、清晰度、倍速和Wi-Fi，记录首开、连续播放或拖动后的具体表现。播放30–60秒后立即运行短诊断，附清晰度/倍速和实际现象。当前无法从官方App读取这些条件，需要用户说明；不要求公开完整视频下载地址。[反馈步骤](USAGE.md)

4K/1.5倍速是否持续无卡顿尚未建立可靠证据，当前自动策略也不是已证明最优的算法。
