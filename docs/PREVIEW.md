# 独立实验候选 · 0.1.20

0.1.19长期订阅和全部旧产物保持原状。这个候选用于验证新改动，**没有完成手机连续播放验收**；仍然只有一个启用开关，不要求挑CDN、线程或DNS。

[实验候选订阅](https://raw.githubusercontent.com/aijc123/Bilibili-Redirect-US/main/dist/preview/BiliBili.Range.Preview.plugin)。只启用这一份下载插件，停用原Redirect与其他Range插件。回退时停用它，再启用[0.1.19](ADAPTIVE.md)；两者统计空间分开，不混用调优记录。

## 这轮解决什么

用户两轮固定范围测速都显示官方下发的Akamai源在该次测试中优于替换CDN：[897,932字节](../benchmarks/phone-media-2026-10-14.json)和[1 MiB](../benchmarks/phone-media-2026-10-14-run2.json)。第二轮原地址1/8任务为20.35/33.43Mbps，全部成功；每档最多2次，摘要未附版本，不能当成0.1.20成绩，也不是原生App基线。

随后[0.1.19普通播放诊断](../benchmarks/phone-playback-0.1.19-2026-10-14.json)显示，59秒新增17次网络错误，近期19次完成接管尝试中9次失败。测速时暂停播放、单个范围组逐次进行；实际接管中存在多个请求重叠，且App下发的原地址也会变化。不能用暂停时的峰值速度推出播放已顺畅，更不能把所有视频强制改到某个Akamai主机。

用户随后补充这轮“好像是杜比视界1倍速，超级卡”。清晰度保留为用户不确定的回忆，严重卡顿是明确反馈；不能沿用此前0.1.17的1080高帧率条件，也不能把旧SIDX表示的码率当作这次杜比视界的实际需求。0.1.20尚无手机结果。

### 网络错误密集时让出下载

同一网络、媒体路径摘要和HTTP/HTTPS，最近8条、60秒内的完成接管样本中，至少3次transport失败且这3次相距不足20秒时：

- 从最后一次失败起15秒内不再接管该媒体的新请求，原请求继续由官方App处理。放行不刷新这15秒，也不假装测到了原生下载速度。
- 随后最多到旧证据60秒过期，只有没有其他有效在途租约时才以**单任务、完整原范围**检查恢复；有其他接管则继续放行，不额外重放媒体。
- 两次后续独立成功后离开这层保护；原有负载、服务器拒绝和近期错误收缩仍生效。再失败会重新计时；单次孤立错误不触发这一层保护。
- 不跨媒体或网络继承；小请求本来就放行。统计有数量和时效上限，并发存储没有原子操作，因此这仍是尽力控制，不保证设备上绝对只有一个恢复请求。

短诊断新增“接管保护”。这是针对可观察错误的恢复策略，不能读取播放器缓冲，也没有证明转圈根因就是并发；放行后App请求的成败不可见。

### 小范围也能比较实际并发

继续复用BTR原分片器与现有ABBA/BAAB规划、5个全成功块、尾部等待约束和20次试探预算。保留128 KiB分片下限，小于256 KiB仍放行。范围不足1 MiB时按实际容量比较：

| 最大实际任务数 | 比较档位 |
| --- | --- |
| 2 | 1 / 2 |
| 3 | 2 / 3 |
| 4 | 2 / 4 |
| 5 | 3 / 5 |
| 6 | 3 / 6 |
| 7 | 4 / 7 |

例如897,932字节实际最多6片，比较3/6，不把配置8当作实际8。1 MiB及以上仍按4/8、满足大小与收益门槛后8/16、16/32递进。试探低档如果首个完整干净块已出现极大退化（比值≥2.5且低档p90超过1.5秒和高档2倍），提前回到已有默认档并冷却，不坚持做完20次。它是止损条件，不是提速结论。

### 端口和网络信息隔离

并发偏好与对照安全暂停增加来源权限域（包含显式端口）的加盐摘要。自动检查在旧0.1.19上实际复现：443路径学到4路后，4483路径也误用了这个偏好；新候选重新积累，不把不同传输端点当成同条件。

另一项检查用真实SIDX二进制复现了旧响应覆盖新网络索引估计的问题：旧响应返回后把新网络的9Mbps示例估计替换为旧网络2Mbps。新候选保留新的信息。这是程序回归样例，**两个数字均不是手机实测码率**；它修复状态一致性，不代表已定位播放卡顿。

## 构建与核对

没有复制整套控制器或修改BTR原文件。`build-adaptive.mjs`提供共用构建函数，仍能生成原0.1.19相同内容；`build-next.mjs`通过检查唯一接入位置复用原控制器，增加小范围与错误退让模块。接入位置变化会构建失败，不静默漏接。历史`dist/next`的0.1.4文件也不覆盖。

```sh
node scripts/build-next.mjs
npm test
node scripts/evaluate-small-ranges.mjs
node scripts/evaluate-small-ranges.mjs --large
node --expose-gc scripts/soak-preview.mjs 1200
```

最后两项只访问本机回环HTTP，使用系统时钟和实际回调。大小矩阵覆盖7种范围、两种带宽配额模型；长期运行覆盖独立/重叠请求、连接断开、实体标记冲突和模拟网络轮次变化，逐字节检查成功响应、等待回调并检查租约释放。模拟网络轮次**不是iPhone真实切Wi-Fi**，也不包含DNS、TLS或解码。执行完成后的原始记录见[大小矩阵](../benchmarks/small-range-matrix.json)与[长期运行](../benchmarks/preview-soak.json)，未完成记录有`complete:false`。

本轮没有修改全局DNS、绕过TLS/签名限制或启动局域网中转。官方公开单请求API尚未确认安全的连接IP覆盖方法，[各DNS返回IP的媒体吞吐](MEDIA-BENCHMARK.md#为什么这次仍不能给dns视频排名)仍未验证。

另外准备了[Custom节点固定IP能力研究](DNS-RESEARCH.md)的独立公开网页探针：先用路由与证书失败对照确认API组合，不直接接触视频地址，也未加入日常菜单。它还没有真机结果，不计为DNS媒体测速完成。

完成结果：267项自动检查通过，生成产物可复现。[小范围矩阵](../benchmarks/small-range-matrix.json)完成14组、448次逐字节校验下载；[4 MiB矩阵](../benchmarks/large-range-matrix.json)完成104次，在每任务独立配额模型选择32任务、共享配额模型选择4任务。这只验证程序能按模型选档，不表示手机应当使用32路。

[20分钟持续运行](../benchmarks/preview-soak.json)完成1,662次请求，其中1,428次响应逐字节一致、234次放行，共10,779个子请求和238次模拟网络轮次变化。该进程HTTP任务峰值16、最大序列化状态67,617字节；不是物理连接数、iPhone内存或播放器成绩。三份记录均完成且对应相同候选产物摘要；本机并行任务存在调度噪音，不据此计算手机提速倍数。

验收仍是[全链路目标](END-TO-END.md)：先复测本次严重卡顿的同视频、用户确认的清晰度和1倍速，再分别验证此前1080高帧率1倍速、持续播放及拖动。不能把放行增多、检查通过或模型提速当成无卡顿证据。
