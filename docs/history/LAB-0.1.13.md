## 32 路是否更快？

这个版本提供每请求 1 / 2 / 4 / 6 / 8 / 16 / 32 路的选择，并增加全局子请求预算 8 / 16 / 24 / 32。默认保持每请求 4、全局 16。已收到真实32小片成功记录，但最新同网络轮次、同表示组、同08c节点的观察中，8路/128 KiB策略优于32路/32 KiB；时间、字节位置与缓存仍有差异，不能视为因果倍数。**目前没有32路更快的可靠真机对照证据。**

默认每片至少 128 KiB，所以 1 MiB 请求最多实际分为 8 片，2 MiB 最多 16 片，4 MiB 才能分为 32 片。仅把 Connections 设为32，不会产生32个小片。诊断分别记录设置的上限和实际片数；这些片数不等于已确认的同时活跃 TCP 连接数。

0.1.8 新增 `MinChunkKiB`，默认128，可手动试64或32。**Connections=32、MinChunkKiB=32、GlobalJobs=32** 才允许一个1 MiB请求分成32个32 KiB子请求。如果预算已有占用，仍可能减小分片数或放行。也可用 `TrialMode=4vs32` 替代固定Connections做交替对照，MinChunkKiB和GlobalJobs仍需设为32。

0.1.13 将首选菜单扩大到15个经过业务参数检查的候选，包括BTR大陆与海外清单的全部12个主机，加上hwo1、08h、alib。选择后确实传给下载脚本、样本诊断及网络预热，路径与签名查询保持原样；新增主机的实际媒体可用性与速度仍待真机验证。另有[每天自动更新的GitHub DNS/TLS快照](../../CANDIDATE-HEALTH.md)，明确不当作手机吞吐排名、不改变已验证的手机选择。

0.1.13 的新安装首选改为 **08c**，依据本项目收到的宾州手机成功传输反馈；原固定重定向订阅的hwo1默认不变。已有安装可能保留旧参数，应手动检查首选。hwo1仍是候选，历史美国测速排名不能保证当前签名媒体在它上面可用。

### 节点使用参考 BTR，适配 Loon 的实际能力

`CDNGroup` 是备用组，**始终保留 PreferredCDN 首选**，不强制把首选切到指定地区。`AutoCDN=false` 时仅使用首选；开启后，优先复用最近10分钟成功、有吞吐记录且未失败/冷却的节点。没有这样的记录、记录过期、节点失败或网络轮次变化后，再按备用组顺序探索。已有多个健康节点时按吞吐评分与20%切换门槛选择，减少来回切换。这不会主动测速所有节点，也不保证找出全球最快节点。

| 备用组值 | 备用候选 | 用途 |
| --- | --- | --- |
| baseline（默认） | 08c、hwo1、hw、ali | 较小的基础回退集合 |
| mainland | ali、hw、bos、08c、bd、14b、estgoss、cos | 参考BTR大陆8节点 |
| overseas | cosov、aliov、香港01-01、香港01-03 | 参考BTR海外4节点 |
| all | 菜单的全部15节点 | 扩大失败回退范围，不在启动时逐个探测 |

分组主机来自[BTR cdn-resolver.js](https://github.com/MrTangLuyao/Bilibili-thread-ripper/blob/0302b345cdfe367ac599b52dc6874e3f7967e220/src/cdn-resolver.js)。成功节点优先与失败回退也参考其思路，Loon选择适配由aijc123实现；范围与SIDX核心继续直接复用原MIT模块。BTR网页可以取得播放器提供的多个原始地址并做流式竞速、取消落后请求；Loon此接口只有当前请求和整块完成回调，所以没有照搬这部分能力。一个接管Range仍只在同一节点切片，并严格校验实体，不跨节点混拼。

32 KiB 是 BTR 原分块工具已支持的下限，分块计算继续直接复用原文件。小片可能减少单片传输时间，也会增加请求和连接调度，不能认定更快；因此默认128保持原样。先观察 p90、错误与放行成本，出现恶化时恢复128。

全局预算同时约束在途接管请求数量（最多 4）、子请求数量和缓冲字节。4 个 1 MiB 请求、每个 8 路、全局 32，可以同时有 32 个 HTTP 下载任务；是否对应 32 条 TCP 连接取决于 Loon 的连接复用。默认总待合并数据预算为 4 MiB；如果接管范围上限增加到 8 MiB，预算才随之提高。拼接时还会申请结果缓冲，字节预算不是整个 Loon 的内存上限。

Loon 持久存储没有原子比较交换，因此跨脚本预算是尽力协调，不承诺严格全局上限。超预算直接交给原请求处理，完成或失败释放租约，异常中断的租约 8 秒后到期。内部请求不再次接管。

更多并发能缓解单连接吞吐受限，但不能突破手机所在网络总带宽。额外握手、请求调度、服务器限流和最慢分片都会影响结果；这个运行方式需要等待整个 Range 下载并校验完毕再返回，不能像电脑播放器一样一边下载一边交付媒体字节。

## 客观诊断能回答什么？

运行「Bili Range 诊断」可得到：

- 最近 30 秒完成的接管尝试交付率，用最早开始到最晚结束的墙钟区间计算，失败尝试时间也计入分母；并行请求不会重复计算时间。另列尝试活跃区间交付率和完成尝试重叠峰值。
- 同网络轮次、同临时媒体表示组、同 CDN、相近请求大小、同在途负载、同实际并发下的样本数、错误比例、吞吐 p50 / p10、耗时 p90。
- 条件相同、精确字节数完全相同、并发设置确实不同且分片数也不同的观察对照。每组至少8个成功样本才达到最低样本门槛。不同字节偏移、缓存和测试时间仍可能造成偏差，所以中位比明确标记为观察值。旧样本缺精确长度时不参与对照。
- 设置并发与实际片数、分片完成时间、重定向次数、网络重置轮次，以及请求数 / 子请求数 / 字节预算分别造成的放行次数。

0.1.8 修正了一个容易误读的比较：固定设置32路时，不同大小的请求自然可能成为6片或8片，这不是调高并发的试验，不能把二者的速率比当成并发收益。普通分布表仍按大小区间展示，观察对照与交替块则采用精确字节数。

实体不一致仍严格放行，不拼接失败数据。新增拒绝字段分类 `total` / `etag` / `last-modified` / `content-type`，便于定位是哪种校验失败；不记录实际ETag或头部值，不降低校验要求。

0.1.10 进一步分类重定向拒绝：格式、外部主机、凭据、HTTPS降级、端口、资源路径包装、其他路径变化。保留原校验和放行行为，只记录固定类别，不保存Location或签名查询。它用于查明此前的13次拒绝原因，再决定是否存在可证明安全的兼容改进。

0.1.12 将普通分布中的「成功p90」和「尝试p90（含失败）」分开显示，避免失败节点耗时在成功分布里消失；最近30秒也列出完成接管尝试的成功/失败数和固定失败类别。已有有效分片耗时样本另外报告最大与最小片耗时之差的p50/p90，用于观察分片不均衡；旧样本缺失这些字段时不推算，耗时差也不能当作可直接回收的等待时间。

手动诊断新增「自上次手动诊断」计数差，包含新增接管、放行及已知原因。第一次建立起点；版本、网络轮次、时钟或计数重置后重新建立起点。起点只在独立本地存储键保存版本/时间/轮次和白名单计数，不复制下载状态、不保存视频地址、不发出额外媒体请求。保存失败会明确提示。它便于区分启动阶段与后段事件，计数差不是吞吐量或卡顿改善证据。

只保存最多 120 条、15 分钟内的本机样本。媒体表示组是带本地随机盐的临时路径哈希，便于归组；它不是密码学匿名化。不会保存或上传原始视频地址、路径、签名、Cookie、Wi-Fi 名称。没有额外后台测速下载。

交付率使用成功返回的字节，统计区间包含成功与失败的已完成接管尝试。它不是严格固定 30 秒的网络接口计数，不含原请求放行流量，也不能测出官方 App 的播放缓冲、实际卡顿次数、真实首字节延迟或视频所需码率。4K / 1.5 倍速是否足够，需要真机播放验证。累计字节除以累计请求耗时尤其不能替代并行流量的墙钟吞吐。

### 用原有播放流量交替比较并发

0.1.6 增加 `TrialMode`，默认 `off`。可选 `4vs8`、`4vs16`、`4vs32`；0.1.11 进一步提供 `8vs16`、`8vs32`，直接对照已经使用的8路与更高上限。打开后忽略固定 Connections，暂时固定使用 PreferredCDN，减少 CDN 变化的影响。它只拆分 App 已发出的合格请求，**不重放视频、不后台多下载一份媒体**。

每 4 个已接管请求组成一个块，随机采用 ABBA 或 BAAB 顺序。A 为所选基线4或8路，B 为所选候选上限。只比较同网络轮次、同临时表示组、同主机、完全相同字节数、同在途负载的完整块；实际分片数量不一致或缺样本会明确计为不一致 / 未完成块。设置 32 但实际只有 8 时会直接显示实际片数，而不是宣称已经测试了 32 条连接。

摘要包含两组错误率、尝试耗时p90（含失败）、成功完整块的速率比，以及至少 5 个成功块后的块重采样经验区间。失败块计入错误比例和耗时尾部，不计入成功速率比。ABBA 能减小缓慢时间漂移的影响，但缓存、原 App 的后续请求时序、服务器变化和样本依赖仍未完全控制；区间不能当作保证或卡顿改善倍数。预算导致的放行流量没有被测量，因此不是整场播放的随机试验。

针对1 MiB主导的请求，试32片的设置为 **TrialMode=8vs32、MinChunkKiB=32、GlobalJobs=32、PreferredCDN=08c**。其他条件保持不变，运行同一视频与清晰度，查看报告是否实际8→32。若实际分片相同、完整块不足、错误增加或p90恶化，不能宣布32更快；结束后关掉TrialMode并恢复表现更好的常规设置。

此功能用于积累可判断的手机证据，暂不根据少量样本自动把默认并发升到32。结束对照时将 TrialMode 改回 off。

### 0.1.13：失败对照先恢复播放

修复对照模式强制固定PreferredCDN却绕过已有失败状态的问题。某次对照下载失败后，暂停同网络轮次、同节点、同签名地址、同对照模式组合10分钟，避免反复在拒绝请求的节点上尝试。恢复流量用该对照的4/8路基线、128 KiB片下限和普通自动CDN选择，不标成对照样本；拒绝/校验失败的原首选会从该恢复候选中临时排除，网络错误仅降低并发并暂停对照，不直接推断节点不可用。

恢复之后从新的平衡块开始，旧失败样本仍保留。更换CDN、获得新签名地址、换另一对照模式或网络轮次可重新检查；旧网络迟到回调不能暂停新网络。这里只保存最多8条带本地盐的地址哈希及固定失败类别，不保存路径、签名查询或完整URL；哈希不是密码学匿名化。这是Loon对照安全恢复规则，参考BTR区分节点与地址失败的做法，未照搬依赖浏览器URL对象和播放器进度的控制器。

目前建议先用 **PreferredCDN=08c、Connections=8、MinChunkKiB=128、GlobalJobs=32、TrialMode=off** 建立恢复基线。8路配全局32允许多个请求分享任务额度；一个请求占满32任务时其他请求可能被预算放行。固定CDN作基线时可关闭AutoCDN；之后再开启或比较其他节点。稳定后才进行8vs32对照，并同时看预算放行与播放体验。已有的32片成功记录证明功能能运行，不证明比8片更快。

## HTTP、DNS 与码率：定位另一类瓶颈

0.1.13 的DNS摘要明确标注每轮1500 ms等待设置与接近上限的回调数量。约1505 ms但带有有效A记录、无错误的回调仍视为成功；不能改标成TIMEOUT，亦不能据此认定AAAA故障。官方API同时查询A与AAAA，并可能续查/重试/回落；它没有阶段时间。Cloudflare第二轮较快可作为进一步对照的候选，但不自动改变手机DNS或断言媒体吞吐改善。

0.1.7 的 `HTTPProtocol` 默认 `h1`，可选择 `h2`，使用 [Loon 官方 HTTP Client API](https://nsloon.app/docs/Script/script_api/) 已公开的 ALPN 参数。偏好会传给每个分片与经过验证的跳转；诊断对两种偏好分别归组，不混为一组。Loon 没有在该回调中报告实际协商协议，所以设置 h2 不等于证明服务器实际使用 h2。HTTP/2 可通过复用减少部分连接开销，也可能共享同一 TCP 连接的拥塞约束，不能用32个任务来推断32条独立连接，参见 [HTTP/2 标准 RFC 9113](https://www.rfc-editor.org/rfc/rfc9113.html)。暂不改变已验证的 h1 默认，也不声称支持该 API 未公开的媒体 HTTP/3。

手动运行「Bili DNS 诊断」会用当前 Loon DNS、[Cloudflare DoH](https://developers.cloudflare.com/1.1.1.1/encryption/dns-over-https/) 和 [Google DoH](https://developers.google.com/speed/public-dns/docs/doh) 各查询4个候选公开主机两轮，最多3个查询并行，工作窗口12秒停止启动新查询。等待已启动回调后结束。要求 Loon Build 988+。它区分缓存命中和非缓存耗时，输出 A / AAAA 数量及错误，不记录默认DNS服务器地址、返回IP或原始错误文本，不下载视频、不修改DNS配置。查询可能填充 DNS 缓存。两轮不能形成稳定排名，而且 API 不提供保持 HTTPS SNI 的指定媒体 IP 能力，因此不能拿解析耗时代替视频吞吐或直接自动换DNS。

码率观察再次直接复用 BTR 的 `sidx.js`，原字节固定、SHA256核验、完整MIT许可保留。它只检查已经成功接管并缓冲的起始响应前64KiB，在其中有完整SIDX时记录索引段的大小 / 时长所估算的表示平均码率和段码率 p90。没有额外索引请求，也没有启用会读取所有视频响应的拦截。小范围初始化常常被放行，因此显示「码率需求未知」是正常结果，不能捏造固定4K码率。

`PlaybackRate` 仅设置诊断假设倍速，默认1.5，不会读取或修改 Bilibili App 的播放倍速。即使看到了索引，也只知道某个已见媒体表示的码率；当前选择、其他音视频表示、传输开销和所需缓冲余量仍未知。报告「平均码率 × 假设倍速」帮助比较供给与需求，不承诺满足此数就不会卡顿。

## 「网络变化」脚本的修复

使用独立入口，不再依赖下载脚本的请求判断。手动运行与网络变化触发都会清空 CDN 旧评分、增加网络轮次、记录重置时间，并明确输出「网络epoch X → Y」。保留当前在途租约，避免重置时重复占用预算。自动触发没有通知。

0.1.10 默认开启 `WarmDNS`：网络变化时对首选与所选备用组中的最多4个公开主机做DNS预热，最多2个查询同时执行。不改DNS服务器、不下载视频、不记录IP或默认DNS地址。结果打印并追加到本轮重置记录，旧网络的迟到回调不能覆盖新一轮。API缺失或查询失败时只报告结果，不阻止已完成的评分重置。可关闭WarmDNS；停用下载开关时也不执行预热。

它针对冷解析的等待，不能提升已热连接的持续带宽。查询是否实际填充后续连接所用缓存取决于Loon运行时，尚无本项目的真机预热效果对照；后台脚本超时设为20秒，DNS单轮为1500ms。

如果只看到 `Script done`，请先更新研发版插件，确认此脚本引用 `network-reset.bundle.js`，再运行；脚本结束标记本身不代表失败。新入口写入失败时会输出失败信息。

## 安装与对照

先停用其他 B 站 CDN / Range 插件，再导入研发版。开启脚本、复写和所需 MITM 信任。Loon [插件官方文档](https://nsloon.app/docs/Plugin/)与 [脚本 API](https://nsloon.app/docs/Script/script_api/)可供查阅。

先保持 4 路作为基线。同视频、同清晰度、同 Wi-Fi 下比较 8 路；再根据诊断决定是否试 16 / 32。每轮主动运行网络变化会清除旧 CDN 评分并创建新的网络轮次，适合隔离网络改变；不要每个视频都重置。对照同一轮的并发时尽量固定 PreferredCDN、关闭 AutoCDN，减少 CDN 变化的混杂。

运行诊断后可点通知复制摘要，粘贴到反馈中。无需分享完整请求记录或签名视频地址。失败时自动放行原请求，但失败的分片尝试已经消耗时间和流量，不是免费回退。

## 第一性原理与参考

稳定播放需要持续有效交付率高于「当前表示的码率 × 播放倍速」，并有缓冲抵御尾部延迟。提升峰值速度、降低失败重试和减少耗时尾部都可能有帮助。DNS 查询速度只影响解析，不能代表 CDN 下载速度；GitHub Runner 的排名也不能代表宾州家庭网络。研发版继续以手机实际传输为主要证据。

- [Bilibili-thread-ripper](https://github.com/MrTangLuyao/Bilibili-thread-ripper)：分块原语直接复用；电脑版控制器能利用播放器缓冲、下载进度和取消信号，Loon API 未提供这些条件，不能照搬后宣称同等能力。
- [Biliverse/Redirect](https://github.com/Biliverse/Redirect)：原重定向项目与维护者 credit。
- [公开 CDN 测速文档](https://github.com/chrisliu298/bilibili-cdn-fix/blob/main/benchmarks.md)：2026-06-11 美国单线路历史数据，作为 hwo1 / 08c 候选来源，不是本研发版的实测速度。

本版本的字节一致性、真实32小片调用、预算、异常租约释放、存储写入失败处理、重定向安全、拒绝分类、DNS预热与网络轮次隔离、隐私字段、精确长度对照、协议偏好、SIDX观察、15节点菜单、区域回退、失败对照恢复与诊断统计通过141项模拟运行检查；32小片、HTTP2偏好、预热与新增CDN的真实播放效果仍待验证。Range CI只读，重复生成研发版并运行这些无需第三方依赖的检查；候选健康工作流另外获准只更新探测快照。上游全套测试另外仍受未安装私有包依赖和原有模板断言限制，不宣称全套通过。

另有 [真实本机 HTTP 并发夹具](../../benchmarks/concurrency-fixture.json)和[可重复执行工具](../../scripts/benchmark-concurrency.mjs)，对4 MiB响应运行1 / 2 / 4 / 8 / 16 / 32路并逐字节校验。2026-10-13 此机器的3轮中位耗时如下；夹具刻意设置120ms初始等待和限速，机器定时器误差也会影响数值：

| 人工条件 | 4路 | 8路 | 16路 | 32路 |
| --- | ---: | ---: | ---: | ---: |
| 仅每下载任务限速 | 1853ms | 940ms | 580ms | 359ms |
| 同时存在共享链路限速 | 1818ms | 1613ms | 1820ms | 1667ms |

这证明实现能够运行32个HTTP任务并正确拼接，也展示共享瓶颈下并发收益会平台化。**表中是人工夹具数据，不能推算 iPhone、海外 CDN 或家庭网络的提速倍数。** Node HTTP 超时语义也不等同于 Loon；该工具不用于验证手机的截止时间行为。

增加 `node scripts/benchmark-concurrency.mjs --small` 的[1 MiB / 32 KiB 小片夹具](../../benchmarks/small-chunk-fixture.json)。同机3轮中位耗时，单任务限速条件下8 / 16 / 32任务为324 / 226 / 190ms；共享链路限速条件下为499 / 529 / 530ms。它进一步验证实际32个小片请求能正确拼接，也说明更多小片可能停在平台甚至略慢。仍是人工本机数据，不是手机预测。
