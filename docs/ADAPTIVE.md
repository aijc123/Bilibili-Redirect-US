## 为什么不能从图里直接选4路

回环图只证明两种指定模型的差异。完成时间可粗略理解为：连接/等待 + 数据量÷可用交付率 + 最慢分片及合并开销。增加并发能缓解单任务瓶颈；链路共享总带宽时收益趋平，更多请求也可能扩大尾部等待。手机、CDN、请求大小和同时播放的音视频都会改变这些项。

原自动版按大小、负载和近期transport错误在4–8路间收缩，并不比较速度收益。候选增加反馈，同时保留完整字节校验、回退、共享预算和小请求放行。

参考[BTR固定版本的自动控制器](https://github.com/MrTangLuyao/Bilibili-thread-ripper/blob/0302b345cdfe367ac599b52dc6874e3f7967e220/src/idm-downloader.js)：升档应检查交付收益，无收益和服务端拒绝后应退档、休息。BTR还能观察缓冲、卡顿、活动字节和队列；[Loon公开API](https://nsloon.app/docs/Script/script_api/)给这里的是完整响应回调，不能虚构播放器信号。候选直接复用已有交替规划、精确匹配和块重采样代码，未复制浏览器控制器冒充手机控制器。

## 自动决策

1. **冷启动保持8路。** 小于256 KiB放行，128 KiB片下限不变。同表示、CDN、精确字节数、当前网络，先积累最近2分钟的8条成功普通请求；连续调优中已有20条近期有效比较请求也能维持准备条件。没有近期数据不算变慢。
2. **比较原本要下载的请求。** 空闲接管时，按随机ABBA/BAAB交替分配；不重放，不额外下载视频测速。比较至少间隔1.5秒，单块最长60秒。学到的偏好也只在这个空闲负载条件下应用：出现其他在途接管时使用原负载策略，不沿用单请求测出的16/32路；恢复空闲后可继续使用原偏好。
3. **比较相邻档。** 先4对8；只有8档收益达标且范围≥2 MiB，才比较8对16；再获益且范围≥4 MiB，才比较16对32。1 MiB正常请求最多8片，不缩小分片伪装32路。
4. **至少5个完整、全成功块才选档。** 每档10条，实际分片必须等于档位；共享预算截断、开始时有负载、观察到重叠、条件不齐或错误不构成升档证据。经验比值区间下界≥1.15，且高档尝试耗时p90不超过低档的1.05倍，才升档。
5. **平台时用低档。** 区间上界≤1.10且低档p90不超过高档的1.10倍，选择低档。每个签名地址/节点/字节长度/网络组合每档比较最多20次；不明确就保留已接受的策略（最初8）。分组15分钟过期后才能重新开始，样本只保留10分钟参与调优。
6. **退化与拒绝要恢复。** 高档首个完整干净块已明显更慢（比值≤0.75）就停止这轮、恢复已有档并冷却3分钟。已选档之后4条普通请求的中位耗时超过原p90的1.5倍，恢复8路并冷却。当前选中节点近3分钟有412/429时用4路、停止调优。普通负载和网络错误收缩仍优先。

签名、HTTP/HTTPS、CDN、长度和网络变化不继承相应比较；新响应观察到ETag/修改时间/类型/总长度标记变化后重新积累。实体标记仅存加盐摘要，不保存原值；无强验证器时不能证明地址内容永不变化。失败仍记在诊断里，不删掉后宣传提速。旧网络回调不能复活旧调优。预算仍是尽力控制；存储无原子CAS，无法宣称严格全局连接上限。

这些是候选工程阈值，不是BTR原参数或播放保证。缓存、时间、范围偏移和未知缓冲仍有混杂；较低档的试验请求可能变慢。Loon不能读取缓冲，无法证明每次比较对播放没有影响，因此候选独立。

## 文件与验证

短诊断增加“并发调优”一行，区分积累、比较、选档、收缩、冷却和预算用尽，不输出媒体地址/签名。小请求放行保留最近有效状态，不刷新其时间；2分钟没有有效状态时只表示状态不可用，不能判断此前是否开始过比较。调优条目最多8个，仅存匿名标识、时刻、档位、耗时基准和暂停时间；原有样本和对照分组另有数量上限。
